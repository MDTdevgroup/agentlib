# Changes & Migration Guide: AgentLib 4.2.0

AgentLib 4.2.0 establishes a unified, extensible tool architecture across in-process tools, MCP servers, and remote A2A agents. It unifies tool registration and dispatch behind a capability-based `ToolSource` contract, turns `ToolLoader` into an indexed facade, upgrades MCP integration to `@modelcontextprotocol/client` 2.x, and introduces automated MCP tool name prefixing.

---

## 1. Unified `ToolSource` Architecture

Previously, local tools, MCP tools, and remote A2A agents built separate tool record shapes that drifted over time. In 4.2.0, all tool providers satisfy a common 5-method capability contract:

```javascript
/**
 * Interface ToolSource:
 * - describe(): ToolSourceDescriptor { id, kind, title, description, connected }
 * - list(): Promise<Array<declaration>>
 * - invoke(name, args, context): Promise<any>
 * - connect(): Promise<void>
 * - close(): Promise<void>
 */
```

### New Source Classes
- [`LocalToolSource`](file:///Users/arsencameron/Documents/peebles/agentlib/src/tools/sources/local-tool-source.js): Encapsulates in-process local functions.
- [`MCPToolSource`](file:///Users/arsencameron/Documents/peebles/agentlib/src/tools/sources/mcp-tool-source.js): Wraps an MCP server connection with automatic caching and event synchronization.
- [`A2AToolSource`](file:///Users/arsencameron/Documents/peebles/agentlib/src/tools/sources/a2a-tool-source.js): Wraps a remote A2A agent peer.
- [`assertToolSource(source)`](file:///Users/arsencameron/Documents/peebles/agentlib/src/tools/sources/tool-source.js): Validates that a custom source conforms to the contract without requiring speculative inheritance.

### Custom Tool Sources
You can register custom tool sources directly into `ToolLoader`:

```javascript
import { ToolLoader } from '@peebles-group/agentlib-js';

const loader = new ToolLoader();
loader.addSource(customToolSource);
```

## 2. MCP Tool Name Prefixing (Breaking Change & Migration)

In earlier versions, MCP server tools were registered using their raw, server-declared names (e.g. `read_file`, `navigate`). When connecting multiple MCP servers (e.g. filesystem and github), tool name collisions were common.

In 4.2.0, tools from MCP servers are namespaced by default as:

```text
${serverName}_${toolName}
```

For example:
- Server `filesystem` tool `read_file` becomes `filesystem_read_file`.
- Server `playwright` tool `navigate` becomes `playwright_navigate`.

### Migration Actions

#### A. Multi-server Setups (Recommended)
Update prompts or expected tool names in your workflows to use the namespaced tool names:

```javascript
// Model invokes the qualified name:
await agent.executeTurn("Read notes.txt using filesystem_read_file");
```

#### B. Single-server / Legacy Opt-Out
If you maintain a single MCP server setup or require unprefixed tool names for backward compatibility, pass `{ prefixToolNames: false }`:

```javascript
// Option 1: On ToolLoader initialization
const loader = new ToolLoader(true, { prefixToolNames: false });

// Option 2: When adding an MCP server
await agent.addMCPServer('filesystem', serverConfig, { prefixToolNames: false });
```

#### C. Unambiguous Raw Name Fallback
If code calls `toolLoader.findTool('read_file')` without a prefix, and only one tool across all sources matches that raw name, `ToolLoader` resolves it automatically during the transition period.

## 3. MCP SDK v2 Migration & Transport Updates

- **Dependencies**: Transitioned from `@modelcontextprotocol/sdk` (1.x) to `@modelcontextprotocol/client` (`^2.1.0`).
- **Streamable HTTP**: Standardized on modern Streamable HTTP (`StreamableHTTPClientTransport`) for remote connections (`type: 'streamableHttp'` or `type: 'http'`). Deprecated `SSEClientTransport` has been removed.
- **Error Semantics**: Tool responses returning `isError: true` throw `Exception('ToolExecutionFailed')` so they flow into the agent's configured `onToolError` policy (`'feedback'` vs `'throw'`).
- **Structured Content**: MCP `structuredContent` is preserved on execution output alongside `content`.
